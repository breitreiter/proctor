Your product has a new user.

Agents are reading your docs and your website. They’re using your API, CLI, or MCP server. How do you measure whether your product helped an agent achieve a goal or reach a correct answer?

Proctor runs real coding agents in sandboxed environments, using the tools, context, and scenarios you provide. Proctor grades each run based on a rubric you define, including static checks, Jev-style deciders, and LLM-as-judge checks. Finally, proctor produces easy to understand reports to help you track how changes affect agent behavior.

The problem

You’ve ticked the agent-readiness box. You have an MCP server or a skill. You added markdown documentation and an llms.txt. You wired it up to Claude and asked the agent to try the feature. You’re done, right? Well, maybe not:

  • The thing you shipped for agents is often not used at all. Vercel ran Next.js tasks end to end and found agents never opened the skill in 56% of runs; a compressed index in AGENTS.md took the same tasks from 53% to 100% (their write-up). Microsoft ran the same upgrade five times per model and found the shipped script executed in none of them (theirs).
  • The agent says it is done when it is not. Stripe built eleven integration environments, graded by calling its own API, and watched agents hit a 400 on bad data and report success; “a mostly correct integration is a failure” (theirs). The agent’s own summary tells you what it planned, not what it did.
  • The fix that worked holds only for the agent you measured it on. A new model version changed Microsoft’s task cost by 3.7× on the same task. Results belong to a named agent, model and version, and have to be rerun when any of those move.

LLMs are non-deterministic. What worked for you once, in your environment, may not work every time for your users. Model behavior changes by family, version, harness, and most dramatically by operating context at runtime. Even with identical priors, a frontier model may approach a complex task in a variety of ways. Proctor measures outcomes, efficiency, and unwanted side-effects, not just strict adherence to an expected trajectory.

This has a name. Agent experience, coined by Netlify’s Mathias Biilmann in 2025 and given a measurable definition by Microsoft’s developer relations team in October 2026: propensity, does the agent find and choose what you built, and efficacy, does it use it correctly. Proctor measures both, independently of any vendor.

How you use it

  1. Define what good looks like. Proctor ships with agent-friendly documentation, examples and skills. Work with your coding agent to define correct outcomes, guardrails and realistic fixtures. Every part of a suite lives on your local filesystem, so you can review it and check it into git.
  2. Try it on an inexpensive model. Make sure everything works before you spend those Anthropic credits.
  3. Confirm on the real thing. Run real harnesses in a safe, containerized environment.
  4. Understand what happened. Start with the report for the high-level view, then dig into the transcripts to see exactly what went wrong. If everything looks good, read a few transcripts anyway, to make sure you’re not grading too leniently or missing bad behavior.
  5. Fix, rerun, compare. Pin the earlier run as a baseline, make your change, and see how the needle moves. Proctor reports every difference with a confidence interval, so it will keep you honest: one good run doesn’t mean the problem is gone.

Coding agents

Models are tuned for their own harness. Claude for Claude Code, GPT for Codex. The same model in a different harness is a different agent, so an eval that runs your tool through anything but the real harness measures something your users will never see. Doing that honestly means a container, a pinned agent version, a shell, a web fetch, your tools, a real repository, several runs. By hand that is a project in itself.

Proctor does it for you:

  • Runs Claude Code, Codex and Qwen Code through Harbor, one container per run, pinned to a version.
  • Checks out the fixture repository and supplies your MCP server, skill, docs or prompt as a bundle the agent can reach. The bundle is the thing under test; the agents are the population.
  • Collects the diff, runs the repository’s acceptance tests in a separate offline verifier, counts turns and tool calls from the agent’s own trajectory.

For when you are handing an agent tools, skills or context and want to know what it does with them: an MCP server, a CLI with agent-facing docs, a skill or plugin, a CLAUDE.md, a documentation site it is meant to follow. Did it find the entry point, reach the outcome, and how many calls did it take?

Assistants and conversations

Not every AI feature is consumed by a coding agent. You might have an in-product assistant, a website chatbot, or a headless job that analyzes data. Those all benefit from rigorous evaluation and verification.

Proctor bundles nb, a thin, highly configurable harness built for visibility and evals:

  • You supply the system prompt, the tool surface and the model. nb runs the conversation.
  • Any model, local or hosted; changing provider is one line.
  • Same transcript shape as the coding-agent runs, so the same checks and report apply.

And proctor can play the user. A task can carry an oracle: a list of what the user knows but did not say.

  • When the model ends a turn with a question, proctor answers from the oracle data, and the conversation goes on until the model stops asking. “I’m looking for some shoes.” “What kind?” “Running shoes, for trails.”
  • Every exchange is recorded, so a check can ask whether the model found out what it needed, how many questions it took, and whether it guessed where it should have asked.

How it grades

Three kinds of check, mixed as a suite needs:

  • Static: no model. How the run ended, turns and tool calls, denials, wall time, diff in scope, your own scripts against the result.
  • Judge: a model sees one named window of the transcript and one question. It must answer with quotes, every quote is verified against the window, and several samples must agree. A split is undecided, never a default.
  • Classifier: a typed classifier reads the window and returns a label with a probability, against a threshold.

Proctor counts turns, tool calls and how a run ended from the trajectory itself. It never takes an agent’s word for its own numbers.

The report

  • Every rate carries a 95% interval and its counts.
  • Arms are compared pairwise on the tasks they share.
  • The minimum detectable effect is stated: three tasks cannot say “no difference” when they mean “could not tell”.
  • Failures are listed by check, with the judge’s quoted evidence.
  • No model writes any of it. A judge’s role ends at a label and a quote.

As of November 2026 we found nothing else that does all three: runs the real agents against a real repository, grades with checks that are deterministic where they can be and quote-verified where they cannot, and reports paired intervals. The scanners and scores that carry the agent-experience label measure conformance to their owner’s checklist. Proctor measures an outcome.

Key concepts

suiteRelated tasks with one goal, graded by one checklist, so a pass rate means one thing.
taskOne prompt against one fixture, with the checks that say whether the outcome was reached.
fixtureThe files a task runs against: a directory or a pinned git revision, with the checks that say what “done” looks like in it. Each run gets a fresh copy, and one fixture can serve many suites.
armOne harness and model, run over every task. The arms are the population; the thing under test is yours.
checkOne yes-or-no question asked of a finished run.
sampleOne attempt at one task by one arm. A task is scored over several.
baselinePinned results from an earlier run, compared with as if it were another arm.

What it is not

  • Not a cloud service. Suites, transcripts, verdicts and reports are files in your repository. The only network traffic is the agents’ model calls and the judge’s.
  • Not a leaderboard. The question is never which agent is best. It is whether what you built works for the agents your users have, and whether your last change helped.
  • Not for single turns. Prompt in, answer out: lighter tools exist, and nb will do it. Proctor is for the long trajectory.

Get started

A .NET tool for Linux. Docker or podman and uv for coding-agent runs; a local or hosted model for the shakedown.

  1. Install and configure.
  2. Run the playground: four commands, no model, no key, and a report about a small TypeScript CLI.
  3. Run the first real suite: a model is asked to make that CLI usable from a script. It waits for a keypress with no --yes and exits 0 when it gives up; we met one like it in the wild.
  4. Move a suite to coding-agent arms, when the question is about Claude Code or Codex rather than the model behind it.
