# Experiment trackers outside LLM work: what to steal for proctor

Scope: MLflow, Weights & Biases, Sacred, Hydra, DVC experiments, plus plain-files tools (guild.ai, meticulous-ml, MLXP). Focus is on run identity, sweep declaration, on-disk shape, re-run/dedup, comparison, and sharp lessons; UIs ignored. Researched 2026-09-17 from official docs, source, and issue trackers.

---

## 1. MLflow (tracking: experiments / runs)

### 1.1 Run identity and joining to inputs
- Run key: `run_id = uuid.uuid4().hex` (32 hex chars), generated by the store (`mlflow/store/tracking/file_store.py`). Optional human `run_name`, auto-generated as adjective-animal-number like `bemused-owl-12`.
- Grouping: an `experiment_id` (integer-as-string, default `"0"`). Parent/child linkage is just a tag: `mlflow.parentRunId`.
- Automatic capture (system tags): `mlflow.source.name`, `mlflow.source.type` (NOTEBOOK/JOB/LOCAL...), `mlflow.user`, `mlflow.source.git.commit` (only when run from a git repo; `mlflow.source.git.branch` only for MLflow Projects), `mlflow.docker.image.name`. Nothing else about the environment is captured automatically for plain runs; `mlflow.log_params` / `log_metric` / `set_tag` are explicit.
- Params are immutable once logged: relogging a key with a different value raises. That is the only "declared input snapshot" guarantee.
- Sources: https://mlflow.org/docs/latest/ml/tracking/tracking-api/ , https://raw.githubusercontent.com/mlflow/mlflow/master/mlflow/store/tracking/file_store.py

### 1.2 Sweeps
- MLflow has no sweep declaration of its own. The documented pattern is one parent run + one child run per parameter combination, linked by the `mlflow.parentRunId` tag; you retrieve children with `mlflow.search_runs(filter_string="tags.mlflow.parentRunId = '<id>'")`. The parent typically holds no params/metrics of its own and should be excluded from comparisons.
- Multiple seeds/trials: recommended practice is to tag both parent and children with family-identifying tags so you can filter and then aggregate mean/std in pandas yourself. There is no built-in aggregation of repeated samples.
- Sources: https://mlflow.org/docs/latest/ml/traditional-ml/tutorials/hyperparameter-tuning/part1-child-runs/ , https://mlflow.org/docs/latest/ml/traditional-ml/tutorials/hyperparameter-tuning/notebooks/parent-child-runs/

### 1.3 On-disk shape (FileStore, `./mlruns`)
```
mlruns/
  <experiment_id>/            # "0", then unique integer ids as strings
    meta.yaml                 # experiment metadata
    tags/ datasets/ traces/ models/   # reserved experiment-level folders
    <run_id>/
      meta.yaml               # run info: run_id, run_name, status, start/end_time, artifact_uri, ...
      params/<key>            # one file per param, value as plain string
      metrics/<key>           # one file per metric, one line per point: "<timestamp_ms> <value> <step>"
                              # (optionally "+ <dataset_name> <dataset_digest>")
      tags/<key>              # one file per tag
      artifacts/              # anything logged as artifact
      inputs/ outputs/        # dataset/model links
  .trash/                     # deleted runs/experiments
```
- Fully greppable: params and tags are single-value files; metrics are whitespace-separated lines (`sort -k3n` for step order). "Latest" metric value = max of the tuple `(step, timestamp, value)`.
- Search implementation loads every run of the experiment into memory then filters/sorts/paginates in Python (`runs.extend(self._get_run_from_info(r) ...)`). Fine for hundreds, bad for tens of thousands.
- Sources: file_store.py above; https://mlflow.org/docs/latest/ml/tracking/backend-stores/

### 1.4 Re-run / resume / dedup
- No dedup. Every `start_run` mints a new uuid. Resuming = `start_run(run_id=...)` on an existing id; nothing checks whether the params match. No sweep-level resume because there is no sweep.

### 1.5 Comparison
- Unit is the run. `search_runs()` returns a DataFrame with flattened columns `params.*`, `metrics.*`, `tags.*` plus run info, with `filter_string` (SQL-ish: `metrics.rmse < 1 and params.model = 'x'`) and `order_by`. Aggregation across repeats is left to the user in pandas.

### 1.6 Sharp lessons
- The plain-files backend is being deprecated (deprecation warning 3.6, SQLite default 3.7 for new users; existing `mlruns` still auto-detected). Stated reasons: dual implementation burden, new features (traces, evaluation datasets, scorers) only on DB, path-traversal security worries, and "performance degrades substantially with high volumes of runs". Migration is `mlflow migrate-filestore --source mlruns --target sqlite:///mlflow.db`; artifacts stay where they are. https://github.com/mlflow/mlflow/issues/18534 , https://mlflow.org/docs/latest/self-hosting/migrate-from-file-store/
- Lesson for a plain-files tool: the layout itself was good (one file per param/tag, line-per-point metrics, meta.yaml per run) and survives fine at single-user scale; what killed it was (a) every query = full scan with no index/summary, and (b) a growing feature surface that had to be re-implemented twice. Keep one storage backend and add a cheap derived index (a single JSONL or CSV of run summaries) rather than a second backend.
- Good: params immutable per run; parent linkage as a plain tag; artifacts stay as files even under the DB backend.

## 2. Weights & Biases

### 2.1 Run identity and joining to inputs
- Run key: `id`, an 8-char random string unless supplied; must be unique in the project and cannot be reused after deletion; forbidden chars `/ \ # ? % :`. Separately a non-unique human `name` (random two words, e.g. `sunny-river-12`), `group`, `job_type`, `tags`, `notes`.
- Three data classes per run: `config` (inputs; keys may not contain `.`; values < 10 MB), `history` (time series via `run.log`), `summary` (final/aggregate values).
- Auto-captured into `files/wandb-metadata.json`: `os`, `python`, `startedAt`, `program`, `codePath`, `args`, `executable`, `host`, `git.remote`, `git.commit`, cpu/gpu info; plus `requirements.txt`, `diff.patch` for uncommitted changes, `output.log`, optional code snapshot (`save_code=True`). System metrics (GPU/CPU/mem) are sampled in the background.
- Sources: https://docs.wandb.ai/ref/python/init/ , https://docs.wandb.ai/guides/runs/ , https://huggingface.co/ncats/EpiExtract4GARD-v2/blob/84933df2fdc6fd184e9fb35d8d72a5b7102f82f8/wandb-metadata.json (real example)

### 2.2 Sweeps
- Declared in a YAML with required `program`, `method` (grid|random|bayes), `parameters` (`values` list, `value` constant, `min`/`max` + `distribution`, `probabilities`, `q`), optional `metric {name, goal, target}`, `early_terminate {type: hyperband, ...}`, `run_cap`, `command` template with macros `${env} ${interpreter} ${program} ${args} ${args_json} ${args_no_boolean_flags}`. https://docs.wandb.ai/guides/sweeps/sweep-config-keys/
- Execution: a server-side sweep controller hands parameter sets to `wandb agent` processes. Runs are ordinary runs tagged with the sweep id; naming/layout is not parameter-derived, it is the usual `run-<ts>-<id>` directory. The sweep itself is the grouping unit; there is no on-disk sweep directory.
- Grid on continuous params "will run indefinitely"; `run_cap` is the guard.

### 2.3 On-disk shape (local `./wandb/`)
```
wandb/
  run-YYYYMMDD_HHMMSS-<id>/          # or offline-run-YYYYMMDD_HHMMSS-<id>/
    files/
      config.yaml                    # config, each key wrapped as {desc: null, value: ...}
      wandb-metadata.json            # auto capture above
      wandb-summary.json             # final summary values
      output.log
      requirements.txt
      diff.patch                     # when repo is dirty
    logs/debug.log, debug-internal.log
    run-<id>.wandb                   # binary record log (protobuf records), the source of truth
    run-<id>.wandb.synced            # marker after sync
  latest-run -> run-...
```
- `config.yaml`, `wandb-metadata.json`, `wandb-summary.json` are readable with `jq`/`yq`. The history (all `run.log` calls) lives only in the binary `.wandb` file; there is no official offline reader (issue https://github.com/wandb/wandb/issues/1768 asks how to read it). To get history you sync to a server and use the export API.
- Sources: https://github.com/wandb/wandb/issues/7227 (offline dir listing), https://github.com/wandb/wandb/issues/9646

### 2.4 Re-run / resume / dedup
- `resume="allow"|"must"|"never"|"auto"` with the same `id` appends to the existing run; `fork_from`/`resume_from` (beta) branch from a step. No dedup of identical configs; a sweep will happily re-run the same grid cell if restarted (grid state lives on the server, so a restarted sweep with a new id starts over).
- Offline mode is a known sore point: `wandb sync` is not automatic; `.wandb` files can be empty/corrupt; config/summary sometimes not written in parallel offline sweeps (issues 6045, 7227, 9646, 6588); third-party helpers (`wandb-osh`, `wandb-offline-sync`) exist to paper over it.

### 2.5 Comparison
- Unit is the run, with optional `group` (and `job_type` within a group). In the UI, grouped runs aggregate as mean/median/min/max with a shaded range of Min/Max, Std Dev, Std Err, or None; the runs table can group-by any config key. Workspace limit of 1,000 displayed runs. https://docs.wandb.ai/guides/app/features/panels/line-plot/reference/ , https://docs.wandb.ai/guides/runs/grouping/
- The "seeds are runs in a group" model is the right shape for N samples per arm: arm = group, sample = run, aggregation = per-group stats.

### 2.6 Sharp lessons
- Got right: automatic environment capture into one small JSON (`wandb-metadata.json`) that is worth copying verbatim as a field list; `config` / `summary` / `history` as three distinct concepts; `group` + `job_type` as the aggregation unit; `run_cap`; `${args}` command templating so the sweep config is the only place params are declared.
- Got wrong for a local user: source of truth is an opaque binary log that needs the vendor server to read; offline mode is fragile and sync is manual; sweep controller state lives server-side so sweeps cannot be resumed from disk; SaaS lock-in and data residency (https://deploybase.ai/articles/mlflow-vs-wandb , https://theneuralbase.com/weights-biases/learn/beginner/w-b-vs-mlflow-hosted-vs-self-hosted-philosophy/).

## 3. Sacred

### 3.1 Run identity and joining to inputs
- Run `_id` is assigned by the first observer (FileStorageObserver: sequential integer dirs `1/`, `2/`, ... or a random `run_<8chars>` depending on version/settings) or set via `--id`.
- Config: built from `@ex.config` scopes (locals of a Python function), `ex.add_config(file)` (JSON/YAML/pickle), `@ex.named_config` variants, and CLI `with a=1 foo.bar=2`. The final frozen config is written as `config.json` per run. `print_config` shows keys marked as "added"/"modified" relative to defaults. https://sacred.readthedocs.io/en/stable/configuration.html
- Seed: Sacred auto-generates a root `seed`, injects it into the config, seeds `random`/`numpy`, and derives per-function `_seed`/`_rnd` deterministically from it, so any run is reproducible with `with seed=123`. https://sacred.readthedocs.io/en/stable/randomness.html
- Auto capture in `run.json`: `experiment.sources` = list of `(filename, md5)` for every imported source file, `experiment.dependencies` (package versions), `experiment.repositories` (git url, commit, dirty flag), `host` (hostname, os, python, cpu, gpus), `start_time`, `stop_time`, `heartbeat`, `status`, `fail_trace`, `command`, `artifacts`, `resources`. https://sacred.readthedocs.io/en/stable/collected_information.html

### 3.2 Sweeps
- None built in. People loop in shell. Combining with `hydra` or writing a driver is the norm.

### 3.3 On-disk shape (FileStorageObserver)
```
my_runs/
  1/                       # or run_<id>/
    config.json            # frozen config incl. seed
    run.json               # all metadata above, status, timings, sources[], host, fail_trace
    cout.txt               # captured stdout/stderr
    info.json              # user-supplied extra info (only if set)
    metrics.json           # {"name": {"steps": [...], "values": [...], "timestamps": [...]}}
    <artifact files>
  _sources/<name>_<md5>.py # content-addressed source snapshot, shared across runs
  _resources/              # content-addressed input files
```
- All JSON; `jq '.status' */run.json` works. Content-addressed `_sources` dedups code snapshots across runs.
- Sources: https://sacred.readthedocs.io/en/stable/observers.html , https://github.com/IDSIA/sacred/blob/master/sacred/observers/file_storage.py

### 3.4 Re-run / resume / dedup
- Statuses: RUNNING, COMPLETED, FAILED (with `fail_trace`), INTERRUPTED (Ctrl-C), TIMEOUT (custom `TimeoutInterrupt`); a heartbeat (every 10 s by default) written to `run.json` lets you detect dead runs (stale heartbeat + status RUNNING). No resume, no dedup; re-running is "run again with the same config". https://sacred.readthedocs.io/en/stable/experiment.html

### 3.5 Comparison
- Nothing built in for files; MongoDB observer + Omniboard/Sacredboard were the UI. For files, people load `*/run.json` + `*/config.json` into pandas.

### 3.6 Sharp lessons
- Got right: the auto-generated seed living inside the recorded config; explicit status enum + heartbeat + fail_trace in one JSON; per-file md5 of sources and a content-addressed `_sources` dir; `config.json` separate from `run.json` (inputs vs outcome).
- Got wrong: essentially unmaintained (last release 0.8.x, 2023); primary observer is MongoDB so the file observer got second-class treatment; no sweep or comparison story at all; "solo investigation only" reputation.

## 4. Hydra (config composition + multirun)

### 4.1 Run identity and joining to inputs
- Hydra does not track runs; it snapshots inputs. Every job writes `${output_dir}/.hydra/` containing `config.yaml` (fully composed user config), `hydra.yaml` (hydra's own config incl. `hydra.runtime.choices`, `config_sources`, `version`, `cwd`, `output_dir`), and `overrides.yaml` (exact CLI overrides list). Plus `<job.name>.log`. No git sha, no env capture (add via your own resolver or MLXP-style wrapper). https://hydra.cc/docs/tutorials/basic/running_your_app/working_directory/ , https://hydra.cc/docs/configure_hydra/intro/
- `hydra.job.name` (from script name), `hydra.job.num` (0..n-1 within the sweep), `hydra.job.id` (launcher-specific, e.g. SLURM id), `hydra.job.config_name`, `hydra.output_subdir` (default `.hydra`, can be null). https://hydra.cc/docs/configure_hydra/job/

### 4.2 Sweep declaration and layout
- Declared entirely on the CLI (`-m db=mysql,postgresql lr=range(0.01,0.1,0.01) schema=glob(*,exclude=w*)`) or in config under `hydra.sweeper.params`. Basic sweeper takes the Cartesian product, splits into batches of `max_batch_size`, and launches. https://hydra.cc/docs/tutorials/basic/running_your_app/multi-run/
- Defaults: `hydra.run.dir = outputs/${now:%Y-%m-%d}/${now:%H-%M-%S}`; `hydra.sweep.dir = multirun/${now:%Y-%m-%d}/${now:%H-%M-%S}`; `hydra.sweep.subdir = ${hydra.job.num}`. The sweep dir also gets `multirun.yaml` (the composed config of the sweep itself). https://hydra.cc/docs/configure_hydra/workdir/ , https://github.com/facebookresearch/hydra/blob/main/hydra/_internal/core_plugins/basic_sweeper.py
```
multirun/2026-09-17/14-03-22/
  multirun.yaml
  0/.hydra/{config.yaml,hydra.yaml,overrides.yaml}  0/my_app.log
  1/.hydra/...
  ...
```
- The much-used alternative: parameter-derived directory names via `${hydra.job.override_dirname}` (now the `hydra_override_dirname` resolver), configurable `kv_sep` (`=`), `item_sep` (`,`), `exclude_keys` (canonical example: exclude `seed` and put it in a subfolder):
```yaml
hydra:
  sweep:
    dir: multirun/${now:%Y-%m-%d}
    subdir: ${hydra.job.override_dirname}/seed=${seed}
  job:
    config:
      override_dirname:
        exclude_keys: [seed]
```
  giving `multirun/2026-09-17/lr=0.01,model=x/seed=0/`. Well-liked because `ls` is the comparison table. Caveats: order of overrides matters for the name, long override lists make long paths, and values with `/` or `=` need escaping.

### 4.3 On-disk shape
- Pure YAML, all human-readable, `yq`/grep friendly. Nothing about outcomes is recorded; Hydra is inputs-only.

### 4.4 Re-run / resume / dedup
- None. `basic_sweeper.py` has no resume/skip-existing logic; a failed job raises when its `return_value` is read but the sweep continues through remaining batches; a re-invocation gets a fresh timestamp dir and reruns everything. Reproduce a single job with `python app.py $(cat .hydra/overrides.yaml | yq ...)` or via the `experiment` config-group pattern. Community plugins (hydra-experiment-sweeper, hydra-filter-sweeper) exist to filter grid combos.
- Issues: https://github.com/facebookresearch/hydra/issues/2614 (want subdir derived from sweep values), https://github.com/facebookresearch/hydra/issues/2790 (sequential sweeps).

### 4.5 Comparison
- None. Hydra is the launcher; comparison is someone else's job.

### 4.6 Sharp lessons
- Copy: the `.hydra/` triple (`config.yaml` = full resolved inputs, `overrides.yaml` = what the human actually typed, `hydra.yaml` = tool config/runtime); `hydra.job.num` as a sweep-local ordinal; override-derived dir names with `exclude_keys` for the seed/sample index; `multirun.yaml` at the sweep root recording the whole sweep spec.
- Avoid: timestamp-only default dir names (unreadable, un-joinable without opening files); no result recording; no resume; the sweeper silently continuing past failures with no index of which jobs failed.

## 5. DVC experiments

### 5.1 Run identity and joining to inputs
- An experiment is a hidden git commit under `refs/exps/<sha[:2]>/<sha[2:]>/<name>` based on `HEAD`; it captures the whole workspace (code, `params.yaml`, `dvc.lock` with dependency hashes, metrics/plots files). The baseline commit is the parent. https://doc.dvc.org/user-guide/experiment-management
- Names auto-generated adjective-noun (`puffy-daks`), or `--name`. Params come from `params.yaml` (or any YAML/JSON/TOML declared in `dvc.yaml`), metrics from files declared under `metrics:` in `dvc.yaml`. `dvc.lock` records md5 of every dep and out per stage, so "exact inputs" is a hash set, not a description.

### 5.2 Sweeps
- `dvc exp run --queue -S 'train.min_split=8,64' -S 'train.n_est=range(100,500,100)'` uses Hydra choice/range syntax and queues the Cartesian product; `dvc queue start -j N` runs them in `.dvc/tmp/exps/` worktrees (Celery-backed). Each becomes its own exp ref. https://doc.dvc.org/command-reference/exp/run , https://doc.dvc.org/command-reference/queue

### 5.3 On-disk shape
- Git objects plus `.dvc/cache` (content-addressed data) and `.dvc/cache/runs/` (run cache). Not greppable without git plumbing; `dvc exp show --json/--csv/--md` is the export. Metrics/params files themselves are ordinary YAML/JSON in the tree.

### 5.4 Re-run / resume / dedup
- Run cache: each stage's signature = hashes of deps + params + command; a matching signature restores outputs instantly ("didn't change, skipping"), disabled by `--force`/`--no-run-cache`, or for stages with `always_changed`, no outputs, or `cache: false`. This is real dedup at stage granularity. https://doc.dvc.org/user-guide/pipelines/run-cache
- Failed queued experiments show status Failed in `dvc queue status`, logs via `dvc queue logs`; you re-queue manually. `--keep-going` continues past failed stages.
- Caveat: dedup by content hash is exactly wrong for stochastic evaluations; you must mark the stage `always_changed` or put the seed/sample index in params so the signature differs.

### 5.5 Comparison
- `dvc exp show`: tree table (workspace row, baseline commit, experiments nested under it) with columns Created, metrics (yellow), params (blue), deps hashes (violet); `--only-changed` drops columns identical across rows; `--drop/--keep <regex>`; `--sort-by <col> --sort-order`; `--csv --json --md`. Identical-param experiments appear as separate rows; no aggregation. `dvc exp diff a b` for pairwise. https://doc.dvc.org/command-reference/exp/show

### 5.6 Sharp lessons
- Copy: `--only-changed` (hide columns that do not vary across the compared rows) is the single most useful comparison affordance in any of these tools; separate params (inputs) from metrics (outputs) from deps (hashes) in the table; the `dvc.lock`-style per-run manifest of input hashes; the idea that a run = one atomic snapshot, and `--md/--csv/--json` output flags.
- Avoid: storing runs as hidden git refs (invisible to `ls`, hard to reason about, bloats `.git`, confuses everyone); content-hash dedup that silently reuses results for stochastic work; Celery queue state.

## 6. Plain-files tools

### 6.1 guild.ai
- Layout: `~/.guild/runs/<uuid4 hex>/` with user outputs at the top level and `.guild/` holding `opref` (operation reference string), `attrs/<name>` one YAML value per file (`id`, `started`, `stopped`, `exit_status`, `pid`, `cmd`, `env`, `flags`, `label`, `deps`, `host`, `user`, `platform`, `vcs_commit`, `sourcecode_digest`, `random_seed`, `initialized`), `LOCK`, `PENDING`, `STAGED`, `output` (captured stdout/stderr) and `output.index`. Short id = first 8 chars. Source snapshot stored per run. https://guildai.org/docs/runs/ , https://github.com/guildai/guildai/blob/main/guild/run.py
- Sweeps: any flag given as a list (`lr='[0.01,0.1]'`) implicitly creates a "batch run" whose trials are ordinary runs linked to the batch; `--optimizer` for random/bayes; trials can be loaded from CSV/YAML/JSON via `@file`. Batch run = parent run on disk; trial = child run.
- Comparison: `guild compare` = terminal table of flags + scalars scraped from `KEY: VALUE` lines in output; `guild runs diff` runs a diff tool on two run dirs. No aggregation.
- Re-run: `--restart <run>` reuses that run's dir/flags/source; `--proto <run>` clones a run as a template. No dedup. Requires no code changes: flags are detected from argparse/globals; that zero-instrumentation stance is why single users liked it. Project is effectively dormant (0.9.x, 2023).
- Lesson: one-attr-per-file makes `cat .guild/attrs/exit_status` trivially scriptable; `LOCK`/`PENDING`/`STAGED` marker files make status visible with `ls`; scraping scalars from stdout is fragile.

### 6.2 meticulous-ml (https://github.com/AshwinParanjape/meticulous-ml)
- `experiments/<N>/` sequential integer dirs containing `STATUS` (RUNNING/SUCCESS/ERROR + traceback), `args.json`, `default_args.json`, `metadata.json` (git sha and message, dirty diff, command, ISO timestamp, description), `stdout`, `stderr`. Reader loads all into a pandas DataFrame. <400 lines, "own your data, no server". Notable: recording defaults separately from args makes "what was overridden" answerable later.

### 6.3 MLXP (https://github.com/inria-thoth/mlxp , https://arxiv.org/abs/2402.13831)
- Hydra multirun for launching; each job gets a uniquely numbered log dir with `metadata/config.yaml`, `metadata/info.yaml` (run status, hostname, git info, timestamps), `metrics/*.json` (one JSONL-ish file per logger key), artifacts. A "version manager" copies the repo at the last commit into a deployment dir and can refuse to run with uncommitted changes. A Reader offers a small query language over stored configs (`config.lr > 0.1 & info.status == 'COMPLETE'`) plus group-by and aggregate (mean/std over seeds) into DataFrames. Explicit motivation: MLflow/W&B too heavy for researchers.

### 6.4 DIY advice that recurs
- https://blog.dagworks.io/p/building-a-lightweight-experiment : one directory per run, config + results as JSON, id derived from a hash of the config.
- https://davidoha.medium.com/10-tips-for-machine-learning-experiment-tracking-and-reproducibility-do-it-yourself-approach-f7c31c533d94 : commit config with code, record git sha and dirty state, never overwrite a run dir.
- Atomic manifest writes (write temp + rename) come up as soon as multiple runs execute concurrently (e.g. https://github.com/AryanXCode646/ARL/issues/20).

## 7. Cross-cutting answers

### 7.1 Run key and join to inputs
| Tool | Key | Inputs snapshot | Auto env capture |
|---|---|---|---|
| MLflow | uuid4 hex + name | params/ (one file per key, immutable) | user, source name/type, git commit (tag) |
| W&B | 8-char id + name/group | config.yaml | wandb-metadata.json (os, python, git remote/commit, args, host, gpu), requirements.txt, diff.patch |
| Sacred | int or run_<id> | config.json (incl. seed) | run.json: sources (md5), deps, git, host, times, status |
| Hydra | job.num within timestamp dir | .hydra/config.yaml + overrides.yaml | none (hydra.yaml runtime only) |
| DVC | exp ref name (adj-noun) on a git commit | params.yaml + dvc.lock hashes | whole workspace commit |
| guild | uuid4 hex | attrs/flags + source snapshot | attrs: cmd, env, host, vcs_commit, sourcecode_digest |

Consensus: key = random id, never derived from params (params-derived names collide on repeats and break when you add a param); join = a small per-run manifest with the resolved config, the literal overrides, git sha + dirty flag, command line, timestamps, host, and tool version.

### 7.2 Sweep declaration and layout
- Declared as: CLI comma/range/glob (Hydra, DVC), YAML `parameters:` with `values` lists (W&B), flag lists (guild), nothing (MLflow/Sacred). Layout: `sweep_root/<job.num>/` (Hydra default), `sweep_root/<override_dirname>/seed=N/` (Hydra idiom), parent run + child runs (MLflow, guild), flat runs sharing a group/sweep id (W&B, DVC).
- Two things every mature setup ends up with: a sweep-level manifest (`multirun.yaml`) recording the full spec, and a per-job ordinal (`job.num`) alongside the random id.

### 7.3 Local storage that works with ls/jq/grep
- Best: Sacred (all JSON), guild (one YAML value per attr file, marker files), Hydra (YAML), MLflow FileStore (one value per file, metrics as space-separated lines), meticulous.
- Worst: W&B (history only in binary `.wandb`), DVC (hidden git refs).

### 7.4 Re-run / resume / partial failure / dedup
- Nobody resumes a sweep from disk except by hand: Hydra restarts everything under a new timestamp; W&B's grid state is server-side; DVC re-queue manually. DVC is the only one with real dedup (stage signature = hashes of deps+params+cmd) and it is a footgun for stochastic runs. Sacred and guild record explicit status + exit_status + heartbeat/LOCK so a dead run is detectable; Hydra records nothing.
- Practical pattern that falls out: make the sweep idempotent by design. Enumerate the grid deterministically, give each cell a deterministic key (hash of resolved arm config + sample index), and skip cells whose run dir already has `status: completed`. Sample index in the key is what DVC's run cache lacks.

### 7.5 Comparison
- Unit is almost always the single run; the group/arm is only a first-class unit in W&B (`group`, aggregated mean/median/min/max with min-max/std/stderr bands) and, via pandas, MLXP. Tables: DVC `exp show` (params + metrics + deps columns, `--only-changed`, `--sort-by`, csv/json/md), guild `compare` (flags + scalars), MLflow `search_runs` DataFrame (`params.*`, `metrics.*`, `tags.*`). None of the file-based tools aggregate repeated samples for you.

### 7.6 Complaints and wins
- MLflow: deprecating the file store for perf/maintenance; full-scan search; feature surface only on DB. Win: simple per-key files, immutable params, parent tag.
- W&B: vendor/SaaS lock-in, opaque binary log, offline fragile, sync manual. Win: `wandb-metadata.json` field list, config/summary/history split, group aggregation, `run_cap`, `${args}` command templating.
- Sacred: unmaintained, Mongo-first. Win: seed in config, status+heartbeat+fail_trace, content-addressed sources.
- Hydra: timestamp dirs, no results, no resume, silent failures. Win: `.hydra/` triple, `override_dirname` + `exclude_keys`, `job.num`, `multirun.yaml`.
- DVC: hidden refs, Celery, hash-dedup vs stochastic. Win: `--only-changed`, lock file of input hashes, md/csv/json output.
- guild/meticulous: dormant, stdout scraping. Win: attr-per-file, marker files, defaults recorded separately from overrides, `--proto` cloning.
